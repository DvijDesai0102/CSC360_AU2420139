# Lecture 4: Canvas Coordinate Geometry, Centered Shape Mathematics, and Repository Configuration

**Date:** 18 August 2026  
**Course:** CSC360: Computer Graphics and Interaction

---

The fourth lecture focused on bridging analytical 2D geometry with practical programmatic rendering on screen, while also exploring critical project hygiene and repository management practices. The session began with an engaging foundational question regarding visual composition: what constitutes the optimal placement of a geometric shape, specifically a square, on a bounded graphical canvas? From both aesthetic balance and computational symmetry perspectives, the ideal placement is achieved when the geometric center of the square coincides exactly with the geometric center of the canvas. This led into a deep exploration of the coordinate transformation required to translate an intuitive center-based mathematical model into the top-left origin coordinate system standard in computer graphics programming.

Because graphical toolkits and rendering APIs typically measure coordinates starting from the top-left corner (0, 0), simply placing a square at the canvas center coordinates (W/2, H/2) results in an offset square where only its top-left corner is centered. To resolve this, we derived the formula to find the top-left starting vertex of the square given a canvas of width W, canvas height H, and a square of side length S. The horizontal starting coordinate is calculated as X = (W - S) / 2, and the vertical starting coordinate is calculated as Y = (H - S) / 2. From this primary reference vertex (X, Y), we systematically determined the remaining three vertices using the known side length: the top-right vertex at (X + S, Y), the bottom-right vertex at (X + S, Y + S), and the bottom-left vertex at (X, Y + S). Understanding this vertex mapping provided clear insight into how bounding boxes, spatial alignment, and geometric centering operate under the hood in rasterization systems.

Building upon these mathematical derivations, we examined the code architecture required to render and style this centered square dynamically. In Java graphics using the Graphics or Graphics2D class, drawing the structural perimeter is achieved via drawRect(x, y, side, side), whereas rendering a solid, filled square requires invoking fillRect(x, y, side, side). We discussed the graphics state machine behavior, where calling setColor() modifies the active paint color prior to invoking fill operations. We reviewed sample implementations demonstrating how to extract panel dimensions dynamically using getWidth() and getHeight() inside paintComponent, ensuring that if the application window is resized, the centering formulas immediately recompute the vertex offsets and keep the square perfectly anchored at the center of the viewport during repainting cycles.

In addition to graphics programming, the lecture addressed essential software development and Git repository architecture. We analyzed the role and security implications of environment configuration files, particularly .env files, which store sensitive local variables, API keys, database credentials, and system-specific paths that must never be exposed publicly. To protect these sensitive configurations and keep repositories clean, we examined the purpose and functionality of the .gitignore file. A properly configured .gitignore ensures that Git automatically ignores tracking build artifacts, compiled class files, target directories, IDE configuration folders, and local environment files. This combination of mathematical precision, graphics implementation, and secure repository management reinforced the essential practices needed for building robust graphical software systems.
